# Concrete design review

Status: Q1-Q85 are accepted. The [manifest specification](manifest-spec.md) and [module design](architecture.md) are the accepted design baseline. The user additionally required broad out-of-the-box coverage for complex abilities without routine Kotlin changes. [ability-coverage.md](ability-coverage.md) makes that requirement concrete. [implementation-status.md](implementation-status.md) tracks current implementation.

## Accepted final round

| Decision | Accepted recommendation | Reason |
| --- | --- | --- |
| Q81: Concrete YAML and module design | Adopt the proposed common grammar and five modules. Keep simple values and effects short, use typed references for reuse, and require named effect IDs only when another declaration addresses them. Begin with one Kotlin mod project containing package-level modules | The draft turns accepted concepts into author-visible spelling, defaults, and extension contracts |
| Q82: Integration with normal Minecraft combat | Route damage through native combat using declared existing damage-type IDs, respecting armor, shields, invulnerability rules, and other native behavior by default. Expose deliberate bypasses only through supported typed mechanics. Report actual health change to after-reactions and progression | A damage amount can mean requested damage or resulting health loss; treating them as interchangeable breaks shields, lifesteal, and kill rewards |
| Q83: Companion dismissal and recall | Distinguish automatic suspension from explicit dismissal. Suspension restores when eligible under Q52/Q63; dismissal persists until a recall action. Reusing a stable companion slot recalls its living companion instead of creating a new identity or refilling health/state. Recall can move it to a safe loaded location near its owner. Dead companions still require revival | Automatic restoration must not undo a player's dismiss order, and resummoning must not duplicate or heal a saved companion |
| Q84: Inventory and block-data recovery | Keep undeliverable item returns in a saved queue for their known recipient. Preserve obstructed terrain restoration data as a durable operator recovery record tied to its original position. Consume recovery records only on successful delivery or explicit restoration, without overwriting later world edits | External changes can end terrain ownership after an original container has been preserved; ordinary cleanup cannot safely discard its contents or guess a new owner |
| Q85: Automatic reload publication | Coalesce approximately 200 ms of stable writes, validate a captured whole set, and apply it at the next server tick. Reconcile affected state together and reject stale client intents without spending resources. Keep asset refresh separate. Valid intermediate multi-file saves may apply; invalid sets keep the last working version | Immediate application still needs coherent files and a single gameplay transition, without a manual apply button or waiting for optional media |

## Accepted integration details

Q81 includes the concrete schema defaults shown in the draft, including constrained YAML parsing, stable grant identities, status cadence and stack modes, state reset defaults, and the shared registration model. The draft is documentation, not a promise that syntax checks prove gameplay behavior. Language and balance examples are illustrative and do not establish required classes.

Q82 uses native outcomes as the source of truth. A prevented or cancelled action has no applied health loss. A source can still react explicitly to prevention or cancellation if that event exposes the relevant result. Native hooks may require Fabric callbacks or focused mixins; the mechanism is an implementation fact to verify, not a manifest feature. Relationship and server PvP restrictions already accepted in Q23 continue to apply.

Q83 defines one companion per stable authored slot for each owner and source class by default. Authors can declare additional bounded slots. The companion record carries living/dead, present/suspended/dismissed, saved location, health, inventory, resources, and timers as separate facts. Recall respects class eligibility and authored costs. A safe same-dimension position is required unless the recall action explicitly supports transfer to the owner's current dimension. A suspended companion never force-loads its saved chunk just to return. An old body discovered later must reconcile against the current incarnation rather than become a second companion.

Q84 distinguishes a return with a known player recipient from preserved world data with no proven inventory owner. The former can be claimed through a recovery view when the recipient has space; the latter requires an operator to choose a valid recovery destination. Full inventories, offline players, removed definitions, or unavailable chunks do not delete the record. Recovery is maintenance behavior, not a manifest escape hatch for arbitrary world writes or item creation.

Q85 interprets immediate as automatic application as soon as stable saved input validates. It adds no reload command, restart, confirmation, or media-download prerequisite. A watcher event alone is not proof of a complete file. State reconciliation is planned before publication so a rejected candidate does not partly change the world or player records. Already completed gameplay and valid permanent terrain edits remain subject to their accepted policies.

## Consolidated confirmation

The numbered policy interview is complete. The additional coverage requirement makes complexity itself insufficient reason to require Kotlin. First compose existing mechanics; improve a reusable built-in operation if a common pattern is missing. [ability-coverage.md](ability-coverage.md) defines the required coverage and evidence. Present the consolidated design for shared-understanding confirmation before implementation. Real Fabric tests remain necessary for native integration and composition scenarios; these are engineering evidence requirements, not deferred v1 features.
