# Runtime behavior design discussion

Status: accepted design. Q71-Q80 define runtime policy; Q81-Q85 complete the integration decisions. [ability-coverage.md](ability-coverage.md) defines the required complex composition capabilities.

## Settled constraints

The server determines gameplay outcomes. Ability starts validate requirements before spending resources and starting cooldowns. Committed costs are not refunded on interruption by default. Effects have declared target types, structured selectors, and filters. Read-only execution contexts expose live values at each step, with explicit snapshots for values captured earlier.

Events caused by abilities can trigger other abilities, but a reaction cannot re-enter its own causal chain and total generated work is bounded. Status reapplication refreshes duration by default; additional stacks require explicit limits. Numeric bonuses use the strongest contribution unless capped addition is requested. Sources remain distinct for cleanup. Summon abilities use the summon as actor and its player as owner.

Automatic valid edits stop affected running abilities and refresh their passives. Required cleanup follows source ownership, including saved terrain restoration and companion state. Completed damage, healing, movement, and permanent terrain changes remain. The accepted policies are recorded in [design.md](design.md), [manifest-authoring.md](manifest-authoring.md), and [summons-and-terrain.md](summons-and-terrain.md).

## Settled decisions

- Q71: Expose before and after phases for supported events. Before hooks can request typed adjustments or cancellation. After reactions see the actual outcome. Process reactions in explicit priority order with stable IDs breaking ties. Finish the current effect and its immediate after-reactions before the next sequence step. Preserve causal ancestry through delays, projectiles, and other resulting effects.
- Q72: Validate targets before committing a new activation, then revalidate each step when it runs. If a target disappears or becomes invalid later, skip that target's affected step and continue independent work. Do not silently choose a replacement. Authors can explicitly request a fresh selection. Preserve committed costs and cooldowns under the existing interruption policy.
- Q73: Stop projectiles on the first eligible entity or blocking block by default, ignoring the shooter and entities excluded by collision filters. Emit an impact once for that collision. An impact that consumes the projectile does not also emit expiry. Provide explicit bounded piercing, bouncing, and homing options, with repeat-hit rules and a finite lifetime.
- Q74: Keep independent status contributions and expiry times per source. Reapplication from the same source refreshes duration without adding stacks unless enabled. Refreshing does not grant an immediate extra tick or restart the periodic schedule. Periodic damage or healing runs independently per source. Boolean restrictions remain applied once while any contribution supplies them. Numeric bonuses keep the accepted strongest-contribution or capped-addition rule.
- Q75: Operators configure hard bounds on work per execution and limits on active objects and per-tick work. Reject known oversized actions before payment. Spread explicitly batchable work, such as large terrain edits, across ticks within its total limit. Runtime hard-limit failures stop the affected execution, clean up its ongoing effects, and report the responsible definition. Completed damage and permanent edits remain.

## Execution details

Q71 does not make the event context assignable. Before hooks use declared operations that request supported changes to the pending action, such as adjusting a damage amount or cancelling it. Ordinary gameplay effects belong in after reactions. The event catalog must state which phases and adjustments each event supports; unsupported combinations are authoring errors. A cancelled action must report a distinct result and must not look like successful damage or healing to an after condition.

Ordering applies to Archetype's own reactions. It does not promise an ordering contract for unrelated mods. Reaction identity should include the acting entity and logical source ability and reaction, rather than a fresh activation ID that would let the same reaction evade recursion checks. Child branches inherit their ancestry; separate sibling reactions do not inherit one another's completed history. Exact source keys and queue order belong in the concrete specification.

For Q72, losing one member of a target set does not cancel effects on the other valid members. A step that depends on a missing result follows that dependency rather than substituting an arbitrary entity. Independent work, such as an effect at a previously captured world position, can continue. Author-selected retargeting still obeys current filters and relationship rules. Starting costs and already completed effects are not implicitly rolled back.

For Q73, an entity collision filter is distinct from which targets a resulting effect may affect. Default harmful projectile filters should agree with the existing ally policy. Piercing, bouncing, and homing do not bypass target validity, finite lifetime, or the common work limits. A default projectile cannot repeatedly hit the same entity; any authored repeat-hit behavior must specify a bounded count or interval. Cancellation and source cleanup are separate from expiry and must not accidentally fire impact or expiry gameplay effects.

For Q74, refreshing a periodic status cannot be used to trigger additional immediate ticks or indefinitely postpone its next tick. Source cleanup removes that source's contribution without removing another source's restriction or bonus. Per-source periodic behavior is deliberately separate from the strongest-source numeric bonus rule. Additional stacks use an explicit cap and do not create additional independent timers by accident. The exact stack-duration options and timing of explicit on-apply effects still need specification.

For Q75, per-tick scheduling limits may defer batchable work; hard total limits terminate work that exceeds them. Ordinary combat event adjustments must not be silently postponed after the underlying action has committed. Pending terrain cleanup retains its restoration records and receives reserved work capacity, so hitting a gameplay budget cannot abandon restoration. Cancelled temporary terrain batches clean up their owned changes. Partial permanent edits remain and are reported; the engine does not promise transactions across arbitrary world effects. Exact default numbers need validation against representative small-co-op workloads during implementation.

## State and presentation decisions

- Q76: Keep a separate resource amount per player and class by default. Allow explicitly shared player-wide resources using one definition and one stored balance. Summons keep their own resources under Q57. Class resources regenerate while that class is active by default. Shared regeneration runs once while at least one active class grants the resource. Offline and absent-summon regeneration pauses.
- Q77: Support declared Boolean flags, named modes, bounded numeric fields, and temporary entity references. Scope state to a class, player, summon, activation, or status instance. Keep it transient by default. Allow explicit persistence for player/class state and persistent companions. Registered effects set, add to, or reset fields; expressions only read them. Resources remain the preferred model for spendable or regenerating values.
- Q78: Keep per-ability cooldowns as the default, with optional named shared cooldown groups, an opt-in global cooldown, and multiple available uses that recharge. Support sequential or parallel recharge, defaulting to sequential. Player cooldowns and recharge timers advance while online even if their class is inactive, and pause offline. Absent-summon timers remain paused. Allow explicit effects that reduce or reset an existing cooldown.
- Q79: Support vanilla resource references and pack-provided icons, textures, and audio, interpreted by Archetype's installed presentation capabilities. Automatically distribute permitted media to clients and refresh client resources after changes. Respect client asset-download choices. Supply built-in visual fallbacks and omit unavailable custom audio. Apply valid gameplay manifest edits immediately without waiting for optional media. New rendering capabilities require Kotlin extensions.
- Q80: Provide editor schemas and a validator that works without launching the game, with readable and structured reports. Report the file, line when available, field path, and invalid value or reference. Add an operator-only in-game inspector for resolved abilities, current state, cooldowns, and failed conditions, plus optional bounded event traces. Ordinary players receive concise ability failure reasons.

## State and presentation details

Q76 separates a reusable resource definition from the location of each current balance. Reusing a definition in two classes does not share the balance unless sharing is declared. A shared resource's base limits and regeneration come from its definition; active source modifiers compose under the accepted numeric rules. Removing one grant does not delete the shared balance or another grant. Resource amounts retain the accepted edit, death, and switching behavior. Any regeneration while a class is inactive must be an explicit policy rather than an accidental second regeneration source.

Q77 adds mutable mechanic memory through declared effects without making expressions, event contexts, or snapshots assignable. Temporary entity references can become invalid and must use the accepted presence and target-loss rules; they are not persistent entity pointers. Transient activation and status state ends with that instance. Class and player persistence requires a declaration, and persistent companion state follows its saved lifecycle. Exact reset fields for death and class changes need to be explicit in the schema. This feature must not become arbitrary collections, executable scripts, or unbounded allocation.

Q78 distinguishes an available use, called an ability charge, from holding input to charge an attack. Recharge counts and timers follow stable logical ability IDs. Changing pages, switching classes, reloading, or applying a behavior replacement must not refill charges. Reducing capacity clamps available charges; increasing it does not grant instant extra uses. Ordinary duration edits affect the next timer started under Q16. A deliberate cooldown-reduction or reset effect can alter an existing timer. Sequential recharge restores one missing use at a time; parallel recharge lets each spent use recover on its own timer.

Q79 requires automatic media delivery without manual file copying. Its transfer mechanism still needs implementation design, including allowed file types, size limits, namespace boundaries, hashes, and client preferences. Resource refresh is asynchronous and distinct from server gameplay-definition publication. Clients use built-in fallbacks while media is unavailable or refreshing; gameplay-critical indicators must remain visible with those fallbacks. Installing a new renderer or registered entity type remains a mod change. Adding media that a supplied renderer or sound adapter can already interpret should not require Kotlin edits.

Q80's validator uses the same interpretation of fields and references as runtime loading. Offline validation checks structure, types, and manifest references using available mechanic descriptions. Checks that depend on the world's loaded registries require matching registry metadata or the running server; missing metadata must be reported as unverified, not as a successful check. The server performs final world-dependent validation. The inspector should explain the effective result of parameters, empowerments, and current grants so an author can find why an ability behaves differently from its base definition. Tracing is disabled by default, bounded when enabled, and identifies source definitions and causal chains. These facilities diagnose ordinary manifest work without adding command execution to manifests.

## Verified asset constraints

Fabric documents a separate client resource reload for `assets/`, distinct from reloading server `data/`. Resource files can change without restarting the game when installed code already knows how to use them. This supports automatic refresh, but it does not establish zero-latency reloads. [Fabric debugging guide](https://docs.fabricmc.net/develop/debugging).

HUD drawing accepts texture identifiers, and Fabric's projectile example can reuse an installed item renderer with item models and textures. Entity types, renderer classes, and animation logic are separately implemented in code. These sources support separating media from new presentation capabilities. [GUI textures](https://docs.fabricmc.net/develop/rendering/gui-graphics#drawing-textures), [Projectile rendering](https://docs.fabricmc.net/develop/entities/projectiles), [Entity rendering](https://docs.fabricmc.net/develop/entities/first-entity).

Sound files and `sounds.json` are resource data, while Fabric's standard sound example also registers a `SoundEvent` in code. Inspection of Mojang's official 26.2 client verified a separate generic client path: `SimpleSoundInstance` accepts an `Identifier`, and sound resolution looks that identifier up in a resource-loaded map populated from `sounds.json`. This permits new pack-authored sound names through installed Archetype playback code without a separate startup registration for every name. The inspected client binary's SHA-1 was verified as `2dc72797acbc1b63fc16a11c4ac393605f453754`. Audible playback and replacement during a live client reload remain integration checks. [Fabric custom sounds](https://docs.fabricmc.net/develop/sounds/custom), [Official 26.2 metadata](https://piston-meta.mojang.com/v1/packages/987b91a95ae93b3bb78cc14d6e0bbd31bad08d59/26.2.json), [Official client binary](https://piston-data.mojang.com/v1/objects/2dc72797acbc1b63fc16a11c4ac393605f453754/client.jar).

Vanilla server-pack delivery includes client download and application status. Required server packs still involve a player prompt and can be declined, resulting in disconnection. These facts do not justify bypassing client preferences in Archetype's delivery design. [Server-pack lifecycle](https://www.minecraft.net/en-us/article/minecraft-java-edition-1-20-3), [Required packs](https://feedback.minecraft.net/hc/en-us/articles/4402626897165-Minecraft-Caves-Cliffs-Part-1-1-17-Java).

These are documentation and binary-inspection checks, not running-client tests. No guarantee has been established for refresh latency, uninterrupted gameplay during reload, or a working asset-transfer implementation in this repository.
